# Public access: phones on any network

The phone app accepts plain `http://` only for `127.0.0.1`. Any other server address must be **`https://` with a valid certificate**.
Phones are usually on mobile data and the server computer on someone's Wi-Fi, so nothing here relies on the same network, LAN IPs or `adb reverse`.

| | Cloudflare quick tunnel | Cloudflare named tunnel | Render |
|---|---|---|---|
| Cost | free, no account | free, Cloudflare account + a domain on Cloudflare | paid instance recommended (free tier sleeps) |
| Address | **new random** `*.trycloudflare.com` every start | fixed, e.g. `https://asha.example.org` | fixed, `https://<name>.onrender.com` |
| Runs on | this computer (must stay on and awake) | this computer | Render's servers, always on |
| Database | SQLite on this computer | SQLite on this computer | managed PostgreSQL |
| Start | `scripts/start_public.sh` | `TUNNEL_NAME=… TUNNEL_HOSTNAME=… scripts/start_public.sh` | push + Render Blueprint |

## 1. Cloudflare Tunnel (on the server computer)

Install `cloudflared`: macOS `brew install cloudflared`; Windows `winget install --id Cloudflare.cloudflared`;
Linux: the package or single binary from Cloudflare's downloads page. Then, after `scripts/dev_setup.sh`:

```bash
scripts/start_public.sh
```

What happens: the backend starts on **127.0.0.1:8000 only** (not reachable from the LAN); `cloudflared` opens an outbound connection to
Cloudflare (no router changes, works behind NAT); the script reads the address from cloudflared's log, polls `<address>/health` until it answers
through the internet (new names take 10–30 s to resolve), writes it to `run/public_url.txt` and prints it with a QR code. The website's
*Settings* and *Phones & users* pages read the same file, so they always show the current address. The script refuses to run if
`AUTH_MODE` is not `api_key`.

Stop everything: `scripts/stop_public.sh`. Windows: `powershell -ExecutionPolicy Bypass -File scripts\start_public.ps1` and `scripts\stop_public.ps1`.
Logs: `run/backend.log`, `run/tunnel.log`.

### Fixed address with a named tunnel (one-time setup)

Needs a free Cloudflare account and a domain whose DNS is on Cloudflare.

```bash
cloudflared tunnel login
```

```bash
cloudflared tunnel create asha
```

```bash
cloudflared tunnel route dns asha asha.example.org
```

Then every time:

```bash
TUNNEL_NAME=asha TUNNEL_HOSTNAME=asha.example.org scripts/start_public.sh
```

Windows: `$env:TUNNEL_NAME="asha"; $env:TUNNEL_HOSTNAME="asha.example.org"` before the `.ps1`. Phones keep the same address across restarts.

### The address changed (quick tunnel)

Every `start_public.sh` with a quick tunnel gives a new address. After a restart: open the website's *Settings* (it shows the new address,
whether it answers, and a QR code) and type the new address into each phone's *Settings → Server address*. Phones keep all unsynced changes
in their outbox until then. To avoid this, use a named tunnel or Render. An admin can also pin an address in *Settings* (e.g. the Render URL).

### Sleep

A sleeping computer means phones cannot sync (they keep working offline and retry later).
- **macOS**: the script runs `caffeinate` while the tunnel runs. Keep the lid open and on power (or System Settings → Battery → Options →
  *Prevent automatic sleeping on power adapter when the display is off*).
- **Windows**: `start_public.ps1` keeps the system awake while the tunnel runs. Closing the lid still sleeps: Control Panel → Power Options →
  *Choose what closing the lid does* → *Do nothing* (when plugged in).
- **Linux**: the script uses `systemd-inhibit` when available.

### Security notes for the tunnel

- Only port-less outbound traffic leaves the computer; nothing listens on the LAN. Authentication is required for every API route except
  `/health` and sign-in; website pages always need a signed-in user.
- Behind the tunnel the server trusts `X-Forwarded-For/-Proto` **from 127.0.0.1 only** (`--proxy-headers --forwarded-allow-ips 127.0.0.1`),
  so rate limits and login lockouts see each phone's own address and session cookies are marked `Secure`.
- For a demo with real people watching, set `APP_ENV=production` in `.env` to hide `/docs`.

## 2. Render (always on, not tied to a computer)

1. Push this repository to GitHub (private is fine).
2. Render → **New → Blueprint** → choose the repository. `render.yaml` creates:
   - `asha-server`: Docker web service from `Dockerfile`, health check `/health`, `APP_ENV=production`, 2 workers;
   - `asha-db`: PostgreSQL 16; its connection string is passed as `DATABASE_URL`;
   - `SECRET_KEY` and `DEVICE_HASH_SALT` generated by Render; you type `ADMIN_PASSWORD` when asked.
3. On first start the container runs `alembic upgrade head`, loads the synthetic data **only into an empty database**, and starts the server.
   Demo-account passwords are random and printed once in the service log unless you add `DEMO_PASSWORD`.
4. Address: `https://asha-server.onrender.com` (the name you chose). Certificate and HTTPS are Render's.

The same image runs anywhere Docker runs (`docker compose up --build` locally with PostgreSQL; Fly.io works with the same Dockerfile).
Migrations: automatic at container start (`alembic upgrade head`). Secrets: environment variables only; `.env.example` lists them.

## 3. Switching a phone between the two

Phone → *Settings* → *Server address* (and *API key*). A key belongs to one server: generate one on the server you switch to.
Records already on that server are pulled; changes still in the phone's outbox are pushed there. Each operation has its own id, so an
operation acknowledged by one server is never re-sent to it; moving data *between* servers is not automatic (use one server per pilot).

## 4. Offline and flaky connections

- The phone keeps every change in its outbox until the server says `acknowledged: true` (after the database commit).
- A push that times out is re-sent with the same operation ids; the server answers `duplicate: true` and stores nothing twice. Tested:
  repeated pushes, 6 identical pushes at once, and 50 phones re-sending a whole batch (`scripts/load_test.py`).
- If the server is busy (SQLite under load) an operation can come back `FAILED_RETRYABLE`, never "acknowledged"; the phone resends it.
